# 交付结构与判定口径

制作结论、矩阵或整改方案时阅读。字段是可选的结构化参考，按任务深度裁剪；不要求每次生成空表。

## 简短审查

优先回答用户的经营决定，包含：

- 在什么事实前提下可以、需要附条件或暂不宜开展；
- 决定结果的主要依据与关键风险；
- 必须先解决的问题、可接受的替代路径；
- 最小补充材料清单和信息补齐后如何改变判断。

避免脱离场景罗列大量法律名称。

## 完整报告

建议顺序：决策摘要 → 范围与业务事实 → 准入判断 → 主要专题分析 → 义务与差距矩阵 → 整改路线 → 待核事项及法源证据索引。

摘要明确评估的业务版本、地区、时点、主要假设和结论范围。将“可以开展部分功能”“整体业务尚有障碍”等局部结论说清楚。

## 合规义务矩阵

| 字段 | 内容 |
| --- | --- |
| O 编号、模块、活动、主体 | 每行对应可独立判断和验收的义务 |
| 义务及触发条件 | 写明谁在何种情况下需要做什么 |
| 履行时点 | 上线前、持续、定期或事件触发；周期需有依据 |
| 法源 | L 编号、条文及性质，不只列法律名称 |
| 已有安排和证据 | 引用 F 编号及材料位置 |
| 履行状态 | 有证据支持已履行／部分履行／有证据支持未履行／待核／不适用 |
| 差距及影响 | 区分事实缺口、制度缺口和执行缺口 |
| 建议行动及验收 | 引用 A 编号，列明可取得的验收证据 |

“不适用”必须说明排除理由；“已履行”必须有与当前范围相匹配的证据。政策文件存在不等于执行有效。

## 风险清单

R 编号｜关联义务｜触发事实｜风险事件及后果｜严重性｜发生可能性｜证据置信度｜是否阻断相关活动｜建议行动。

- **严重性**：结合处罚、用户损害、交易效力、业务中断和整改可逆性评定。
- **发生可能性**：基于现有行为、暴露范围及可核实监管实践；没有依据时不虚构概率。
- **置信度**：反映事实和规则的完整性，可使用高、中、低并解释原因。
- **阻断性**：单独判断，不能由平均分决定。

高、中、低风险只是本项目的管理工具，不应被表述为统一法定分类。精确罚款区间、时限或金额阈值必须来自核验后的适用条款；法定上限不等于预期处罚。

## 整改计划

A 编号｜关联风险/义务｜具体措施｜建议责任角色｜前置依赖｜完成时点｜交付物｜验收标准｜剩余风险。

时点优先采用“上线前”“扩大业务前”“事件发生后依法定期限”等业务节点。提出内部目标日期时标注“建议”，不得写成法定期限。未知责任人使用职能角色，不编造姓名。

验收标准应可验证，例如取得覆盖相应主体与业务的许可、成功完成取消订阅流程测试、形成并落实数据访问权限清单；“加强管理”“注意合规”不能独立作为整改完成标准。

## 路径比较

方案｜实际业务变化｜新增条件｜缓解的风险｜未消除风险｜实施约束｜结论及前提。

比较用户需要选择的实质不同路径，不为凑数量提供无实际差别的方案。成本与周期没有资料时使用待估范围或定性说明，不给出伪精确数字。

## 文件交付

- Markdown 适用于对话答复和简短备忘录。
- DOCX 适用于正式报告；保留可编辑表格和可追溯引注。
- XLSX 适用于跨部门分工及持续跟踪；可按业务事实、准入、义务差距、风险整改、法源证据组织工作表，避免重复维护同一结论。

若使用文档或表格技能，按实际可用能力生成并检查输出。没有文件生成能力时提供完整可复制内容，不声称文件已创建。

如要求持续跟踪，报告中列明重新评估的触发事件，例如新增地域、功能、客群、资金路径或数据用途。未经用户请求，不自动创建监控任务。
